# 02 WBS 文档

> 要求：WBS 必须围绕交付物（成果）分解，至少分解到三级。

## 1. 一级交付物

本组依据《校园活动报名与签到管理系统》项目目标与WBS面向可交付成果分解的原则，将项目整体分解为以下五个主要成果域：

1. 项目管理成果
2. 需求分析成果
3. 系统设计成果
4. 功能模块成果
5. 测试与验收成果

## 3. 分解说明

本组WBS分解的核心思路是以最终交付成果为出发点，从整体到局部逐层细化，确保每项工作都有明确、可验证的产出物。

1. **一级成果域围绕最终提交物展开**：我们将项目结束时必须提交的成果归纳为五大类——项目管理文档、需求分析结果、系统设计产物、可运行的功能代码、测试记录与验收报告。这五类成果覆盖了从管理、设计到开发、验证的完整链条，任何一类缺失都会导致项目交付不完整。以成果域作为第一级划分，有助于在项目启动阶段就明确“最终要交付什么”，避免陷入按部门或按阶段分工的传统思路。

2. **二级与三级体现从子系统到具体产出的细化层次**：二级条目将每个成果域拆分为相对独立的子成果。例如“功能模块成果”下分为活动管理、报名管理、签到管理、统计导出和用户文档五个子系统，每个子系统本身就是一组功能相关的交付物集合。三级条目进一步细化到单个文件或单个功能点，如“活动发布与信息维护功能”是一个边界清晰、可独立测试的功能单元，“活动基本信息结构定义”是一个明确的源码文件。这样逐层展开后，最底层的每个条目都可以直接指派给一名成员负责，也便于评估工作量和跟踪完成状态。

3. **三级条目作为工作包，衔接后续进度安排**：在WBS中，每一个三级条目就是一个工作包，是分解的终点。它们不再继续向下分解，但在后续制定进度计划时，会将这些工作包进一步转化为具体活动。例如“二维码生成功能”这个工作包，在进度计划中可能会对应“编写二维码生成逻辑”“编写生成接口”“接口联调”“功能测试”等一系列活动。这样保证了WBS本身的稳定性，同时为进度安排留有灵活空间。

4. **全文统一使用成果化描述，不出现动作类词汇**：WBS描述的是“做完这件事产生了什么”，而不是“做了什么事”。因此本组在整个分解中所有条目均使用名词性短语，如“活动发布与信息维护功能”“签到记录数据结构定义”“测试用例清单”等。像“开发活动模块”“进行数据库设计”“讨论接口方案”这类以动作或过程为主的表述，虽然在实际工作中确实会发生，但它们不构成可移交的成果，因此不出现在WBS中。这样做的目的是让每一条目都具备可验证性——任何人在任何时候拿到这个条目，都能判断它是否已经完成。
