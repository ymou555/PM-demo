## 1. 本组项目组织情况

本项目小组由三名成员组成，围绕“校园活动报名与签到管理系统”项目展开协作。

### 1.1 组织方式

采用 `“角色分工 + 分支隔离 + 合并审核”` 的三层协作模式。每位成员根据角色认领对应的功能分支，在各自分支上独立工作，互不干扰。阶段性成果由项目经理审核后，配置管理员合并至 `dev` 分支并打版本标签。最终版本由项目经理将 `dev` 合并至 `main` 分支完成提交。

### 1.2 角色配置与分工依据

| 姓名 | 角色 | 具体分工 |
|---|---|---|
| 张景元 | 项目经理/计划负责人 | 统筹项目进度与最终提交；负责 WBS 分解文档、项目启动说明、README 和总结报告的编写；参与冲突解决 |
| 陈佳圻 | 计划负责人/协作成员 | 负责简化进度计划文档、项目启动说明文档和总结报告的编写；参与文档完善、分支提交与冲突解决 |
| 向家兴 | 配置管理员 | 负责仓库、分支合并管理与冲突解决；负责配置管理文档和总结报告的编写 |

**分工依据**：

- **陈佳圻担任计划负责人/协作成员**：进度计划基于 WBS 提取活动、估算工期、梳理前置关系，逻辑性强、可独立推进，适合专人负责。作为协作成员，同时参与其他文档的完善与校对，使每份文档都经过至少两人审阅，降低内容遗漏和表述不一致的风险。

### 1.3 组织特点

- 每位成员有明确的分支、文档和操作职责，避免任务重叠或遗漏。
- 各成员在独立的功能分支上工作，不会直接修改他人文件，减少冲突概率。
- 文档由项目经理统一审核内容质量，配置管理员进行二次确认并合并打标签，双重保障成果质量。
- 所有提交、合并、标签操作均在 Git 中留有完整记录，便于追溯每位成员的贡献和项目演进过程。

## 2. WBS 分解思路

本组WBS分解的核心思路是以最终交付成果为出发点，从整体到局部逐层细化，确保每项工作都有明确、可验证的产出物。

1. **一级成果域围绕最终提交物展开**：将项目最终交付成果归纳为项目管理文档、需求分析结果、系统设计产物、功能模块代码、测试与验收报告五大类，覆盖从管理到验证的完整链条，在项目启动阶段就明确“要交付什么”。

2. **二级与三级体现从子系统到具体产出的细化层次**：二级条目将各成果域拆分为相对独立的子成果，三级条目进一步细化到单个文件或功能点，边界清晰、可独立测试，便于指派和跟踪完成状态。

3. **三级条目作为工作包，衔接后续进度安排**：每个三级条目即为一个工作包，是分解终点。在后续进度计划中，工作包被进一步转化为具体活动并排定工期和责任人，保证WBS稳定性的同时为进度安排留有灵活空间。

4. **全文统一使用成果化描述，不出现动作类词汇**：所有条目均使用名词性短语描述产出物本身，不出现“开发”“讨论”“联调”等过程性表述，确保每一条目都具备可验证性。

## 3. 进度安排依据
1. 依据《校园活动报名与签到管理系统》三级 WBS 分解结构，提取关键活动，确保进度计划与交付物一一对应。
2. 遵循软件工程标准流程，确定任务间的先后依赖关系，核心流程为：项目初始化 → 需求分析 → 系统设计 → 功能开发 → 测试验收，保证开发流程规范合理。
3. 结合系统规模、任务复杂度及团队协作效率，合理估算每项活动的工期，确保计划可落地、可执行。
4. 依据团队成员角色与职责分工分配责任人，明确权责，提升协作效率。
5. 结合配置管理方案，将分支策略、版本管理等工作纳入进度计划，保障项目过程规范化。

## 4. 配置管理与协作过程
### 4.1 配置管理目标与原则

**配置管理目标**：
- 确保项目资产的完整性和可追溯性
- 支持团队并行开发，减少冲突
- 提供稳定的版本发布能力
- 便于问题追溯和快速回滚

**配置管理原则**：
- **唯一性**：每个配置项有唯一标识
- **完整性**：记录所有变更历史
- **可追溯性**：任何变更可追溯到来源
- **一致性**：保持文档与代码同步

### 4.2 版本控制策略

本项目采用 Git 作为版本控制工具，使用简化的分支管理模型：

- **main 分支**：默认分支，存放稳定的生产版本代码
- **dev 分支**：主开发分支，包含最新的开发代码
- **feature-* 分支**：功能开发分支，从 main 分支创建，完成后合并回 dev

**实际创建的功能分支**：
- `feature-charter`：项目章程功能模块
- `feature-config-plan`：配置计划功能模块
- `feature-schedule`：进度计划功能模块
- `feature-summary`：总结报告功能模块
- `feature-wbs`：WBS 分解功能模块

### 4.3 代码提交规范

采用统一的提交信息格式，便于追溯和自动化处理：

```
type(scope): description

[optional body]

[optional footer]
```

**type 类型说明**：
- `feat`: 新功能
- `fix`: 修复 bug
- `docs`: 文档更新
- `style`: 代码格式调整（不影响逻辑）
- `refactor`: 重构代码
- `test`: 测试相关
- `chore`: 构建/工具相关

### 4.4 配置管理工具

| 工具 | 用途 | 版本 | 实际应用 |
|------|------|------|----------|
| Git | 版本控制 | 2.40+ | 管理代码版本和分支 |
| GitHub | 代码托管与协作 | - | 托管代码仓库，分支协作 |

### 4.5 协作沟通机制与流程

**沟通机制**：
- **即时沟通**：使用微信进行日常沟通、任务分配和问题讨论
- **文档协作**：使用 Markdown 文档进行项目文档编写和共享
- **代码协作**：通过 GitHub 进行代码托管、分支管理和 Pull Request 协作

**协作流程**：
1. **分支创建**：成员基于main分支创建个人feature分支进行开发
2. **功能开发**：每位成员在各自的 feature 分支上完成文档编写
3. **合并到 dev**：配置管理员审核后，将各 feature 分支合并到 dev 分支
4. **最终审核**：所有功能完成后，由项目经理进行整体审核
5. **合并到 main**：审核通过后，将 dev 分支合并到 main 分支完成发布

## 5. 冲突解决过程记录

### 5.1 冲突制造

本组三名成员分别在各自的功能分支上对 `docs/conflict.md` 文件的“当前结论”一行进行了不同修改：

| 成员 | 所在分支 | 修改内容 |
|------|----------|----------|
| 张景元 | feature-wbs | 当前结论：各成员在功能分支开发，完成后由配置管理员合并至 dev，最终审核通过后再从 dev 合并至 main。 |
| 陈佳圻 | feature-schedule | 当前结论：本组决定直接合并到 main。 |
| 向家兴 | feature-config-plan | 当前结论：本组决定由配置管理员负责所有合并。 |

三人各自在本地修改后，分别提交并推送至远程对应分支，提交信息均使用 `docs` 类型标识。

### 5.2 冲突识别

配置管理员向家兴在本地将三个功能分支依次合并至 dev 分支。首次合并 feature-wbs 时无冲突，顺利通过。继续执行 git merge feature-schedule 时，Git 输出如下提示：

    Auto-merging docs/conflict.md
    CONFLICT (content): Merge conflict in docs/conflict.md
    Automatic merge failed; fix conflicts and then commit the result.

打开 docs/conflict.md，冲突位置的标记如下：

    <<<<<<< HEAD
    当前结论：各成员在功能分支开发，完成后由配置管理员合并至 dev，最终审核通过后再从 dev 合并至 main。
    =======
    当前结论：本组决定直接合并到 main。
    >>>>>>> feature-schedule

随后继续合并 feature-config-plan 时，同样因同一位置存在差异，再次触发冲突。

### 5.3 冲突解决

配置管理员定位冲突文件后，通知其他成员共同协商。经讨论决定保留 `feature-wbs` 分支的方案作为最终内容：
- 当前结论：各成员在功能分支开发，完成后由配置管理员合并至 dev，最终审核通过后再从 dev 合并至 main。

协商确定后，由项目经理张景元先在本地合并 `feature-wbs` ，随后合并 `feature-schedule` ，打开 `docs/conflict.md`，手动选择需要保留的内容，解决冲突。同理处理 `feature-config-plan` 合并时产生的冲突后，三个功能分支全部成功合入 `dev` 分支。最后完成提交和推送。

### 5.4 最终结果

- 冲突文件：`docs/conflict.md`
- 涉及分支：`feature-wbs`、`feature-schedule`、`feature-config-plan`
- 涉及成员：张景元、陈佳圻、向家兴
- 协商结果：采用 `feature-wbs` 分支的合并策略方案
- 解决方式：由项目经理张景元手动选择保留内容并完成合并提交
- 合并状态：全部功能分支成功合并至 `dev`，无遗留未解决的冲突
- 冲突文件保留在仓库中作为冲突练习的完整记录，整个过程可完整追溯

## 6. 经验与问题

### 6.1 实验收获

**对软件项目管理的理解更加具体**。通过本次实验，我们体会到项目管理不仅仅是编写代码与文档，更是对项目范围、进度和配置的统筹协调。WBS 的编制让我们学会了如何将模糊的项目目标逐层拆解为可管理、可验证的工作包；进度计划的制定让我们理解了活动之间的前置依赖关系对工期安排的影响；配置管理文档的编写和实际执行则让我们认识到统一的命名规范和分支策略对团队协作效率的重要性。

**Git 协作能力显著提升**。实验过程中，我们从创建仓库、建立分支、独立开发、合并提交到制造并解决冲突，完整体验了 Git 团队协作的完整流程。特别是冲突解决环节，让我们真正理解了合并冲突的产生机制和手工解决的方法，而不仅仅是知道理论概念。每位成员都掌握了 `git add`、`git commit`、`git push`、`git pull`、`git merge`、`git tag` 等基本操作，并能够独立处理推送被拒、分支落后等常见问题。

**团队协作意识增强**。通过角色分工和分支隔离的协作模式，我们体会到明确职责边界对团队效率的重要性。项目经理统筹全局、计划负责人专注进度编制、配置管理员维护协作基础设施，各司其职又相互配合，避免了任务重叠。日常沟通中遇到问题及时在群内协商，确保了信息的及时传递和决策的高效执行。

### 6.2 遇到的问题

1. **提交信息格式的规范执行**：项目初期的初始提交和 README 分工提交未遵循 `<类型>: <简要描述>` 格式，因为当时配置管理规范尚未制定。在配置管理文档确立了提交信息规范后，后续所有提交均严格按照约定格式执行。协作规范不宜滞后，应在项目启动阶段就尽早确立并同步给全体成员。

2. **Git 提交人名称设置**：实验要求每位成员的 Git 提交人名称统一设置为本人姓名的拼音全称，初次操作时对配置方法不熟悉，通过搜索和查阅资料，掌握了 `git config user.name` 命令的使用方式，随后各自在本地完成配置。

3. **标签打完后发现遗漏**：在打完 v1.0 标签后，发现少合并了一个功能分支的内容。由于标签一旦推送即固定指向某次提交，无法直接修改，只能先执行 `git tag -d v1.0` 删除本地标签，再执行 `git push origin --delete v1.0` 删除远程标签，补合遗漏分支后重新打标签并推送。在打标签前应仔细核对 `dev` 分支是否已包含所有应合入的功能分支，避免重复操作。

4. **合并冲突处理经验不足**：在将多个功能分支合并至 `dev` 时，由于三名成员都修改了 `conflict.md` 的同一行，连续产生了两次合并冲突。初次面对冲突标记时，对如何定位冲突、如何协商解决方案、如何手工编辑文件还不够熟练，但通过实践操作，最终顺利完成了冲突解决。

5. **误提交多余文件**：在使用 `git add .` 时未仔细检查工作区文件，误将多余文件提交至功能分支。检查后删除多余文件并重新提交。后续在执行批量暂存操作前应先确认待提交文件清单，避免引入多余内容。

### 6.3 改进方向

- 制定协作规范后，在项目初期就进行一次演示或检查，确保所有成员理解和遵守。
- 遇到技术问题时及时在群内沟通，避免个人长时间独自排查而影响进度。
- 在合并分支前先执行 `git fetch` 确认远程状态，尽量避免本地与远程分叉导致的额外合并。
