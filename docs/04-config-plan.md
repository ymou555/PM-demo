\# 04 配置管理文档



\## 1. 配置项范围

\- README.md：项目说明与仓库使用说明

\- 项目启动说明（01-xxx.md）

\- WBS 分解文档（02-wbs.md）

\- 进度计划文档（03-schedule.md）

\- 配置管理文档（04-config-plan.md）

\- 项目总结报告（final-report.md）

\- 示例代码或资源文件（assets/、src/、test/ 目录下文件）



\## 2. 分支策略

\- `main`：主分支，仅用于存放已完成、经过审核的最终代码与文档，不允许直接提交

\- `dev`：开发分支，用于合并所有 feature 分支的阶段性成果，是 `main` 的前置分支

\- `feature-\*`：个人开发分支，命名格式为 `feature-姓名拼音`，所有成员的日常开发、修改、提交都在自己的 feature 分支上进行



\## 3. 命名约定

\- 文档命名：`0x-名称.md`，如 `03-schedule.md`

\- 分支命名：`feature-姓名拼音`，如 `feature-XiangJiaxing`

\- 提交说明：使用「类型: 描述」格式，如：

&#x20; - `feat: 完成03-schedule.md进度计划文档`

&#x20; - `fix: 修正WBS文档的前置关系错误`

&#x20; - `docs: 更新配置管理文档内容`



\## 4. 合并规则

\- 合并负责人：配置管理员（向家兴），项目经理（张景元）审核

\- 合并时机：

&#x20; 1.  阶段性任务完成后，由成员提交 Pull Request（PR）到 `dev` 分支

&#x20; 2.  所有成员任务全部完成、通过审核后，再合并 `dev` 分支到 `main` 分支

\- 冲突处理：

&#x20; 1.  先在本地 `feature` 分支合并 `dev` 分支，解决冲突后再提交 PR

&#x20; 2.  冲突由修改相关文件的成员共同协商解决，配置管理员协助完成



\## 5. 版本留痕

\- 所有提交必须保留清晰的提交说明，关键提交需在文档中备注

\- 每个阶段完成后，在 `dev` 分支打一个轻量标签（tag）记录版本

\- 不删除任何历史分支与提交记录，所有修改可通过 Git 历史回溯
